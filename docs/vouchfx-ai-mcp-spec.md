## 0. How to use this document (instructions for Claude Code)

You are implementing an AI/agent layer on top of the existing **vouchfx** repository (`github.com/tomas-rampas/vouchfx`), an end-to-end integration testing framework for distributed systems authored in YAML (`.e2e.yaml`), compiled to C# via Roslyn, orchestrated with .NET Aspire + Testcontainers.

Ground rules for the implementation session:

1. **Inventory before you change anything.** Start by reading the repo: solution layout, the existing MCP server project, the DSL JSON Schema, the AST/compiler, the provider registry, the JSON Lines event envelope, the CLI, the samples repo (`vouchfx-samples`). Produce a short written map of *where each concept in this spec already exists* and *what its actual names are*. Where this spec's names differ from the codebase, **the codebase wins** — adapt the spec's names, keep its semantics.
2. **Do not touch the engine's runtime contracts.** The frozen v1.x provider contract (`IStepProvider`, `IStepBinder<T>`, `IStepValidator<T>`, `IStepCompiler<T>`, `IResourceContributor<T>`), the DSL schema (except additive, versioned changes explicitly called out here), the memory model (compile-once, collectible `AssemblyLoadContext`, `.Unload()`), and the verdict taxonomy are **read-only** for this work. The memory-leak regression CI gate must stay green.
3. **Milestone by milestone** (Section 12). Each milestone ends with its acceptance criteria passing, tests added, and a PR-sized change. Do not start the agent layer (M5+) before the deterministic layer and MCP tools (M1–M4) are done and tested.
4. **Deterministic first.** Anything that can be computed without a model (topology extraction, validation, compilation, impact analysis, verdict summarization) must be a plain .NET library with unit tests. The model only *proposes*; the engine and its validators *decide*.
5. **Ask when the repo contradicts the spec** in a way that changes semantics (not naming). Otherwise proceed.
6. Language/runtime: match the repo (.NET 8 LTS today; if the repo has moved to .NET 10, follow the repo). C# 12+, nullable enabled, `record` types for models, `System.Text.Json` with source-generated contexts for all wire models.

## 1. Purpose, scope, non-goals

### 1.1 Purpose

Make vouchfx the E2E testing tool that AI coding agents can use **correctly and safely**, and ship vouchfx's own agents (Author, Healer, Impact) for CI and CLI use.

The thesis: a constrained declarative DSL validated by a JSON Schema and a compiler is the only reliable substrate for LLM-generated tests. Free-form imperative test code generated by generic assistants is brittle; a `.e2e.yaml` proposal is rejected by the schema before a container starts and by the compiler before a delegate runs. This spec turns that property into a product surface.

### 1.2 Scope (this spec)

1. **Deterministic libraries** (no model dependency): topology extraction, static impact analysis, verdict/event-stream summarization, spec authoring helpers.
2. **MCP server** (extend the existing one): a complete tool/resource/prompt surface so that any MCP host (Claude Code, GitHub Copilot, Cursor, VS Code agent mode, Microsoft Agent Framework agents) can author, validate, compile, run, inspect, and maintain vouchfx scenarios.
3. **Agent layer** (`vouchfx.ai`, separate package) built on **Microsoft Agent Framework 1.0** (.NET): Author, Healer, Impact agents, exposed as `vouchfx ai <command>` and as a GitHub Action.
4. **Safety, audit, telemetry** rules for all of the above.

### 1.3 Non-goals

- No changes to the engine's execution semantics, provider contract, or memory model.
- No UI/browser testing, no unit-test generation.
- No hosted/SaaS agent runtime in this phase (Foundry Hosted Agents / Agent Harness are explicitly out; local CLI + CI only).
- The AI package must not become a dependency of the core engine, the CLI core, or any provider.
- No model fine-tuning; no telemetry that leaves the user's machine without explicit opt-in.

## 2. Design principles (normative)

| # | Principle | Consequence |
|---|-----------|-------------|
| P1 | **Core stays model-free** | `vouchfx` (engine, CLI, providers) has zero dependency on any LLM SDK. All AI code lives in `Vouchfx.Ai.*` packages. |
| P2 | **Schema and compiler are the guardrails** | Every agent-produced spec passes `validate_spec` and `compile_spec` before `run_scenario`. No tool bypasses validation. |
| P3 | **Deterministic before probabilistic** | Topology, impact, and verdict summaries are computed by code with tests. Agents consume these as facts. |
| P4 | **YAML-only writes** | Agents (and the `write_spec` tool) may only create/modify files under the configured specs directory with `.e2e.yaml` extension. Never providers, engine, CI config, or secrets. |
| P5 | **Verdict taxonomy is the control signal** | `Pass` / `Fail` / `EnvironmentError` / `Inconclusive` are never conflated. Healer acts only on `EnvironmentError` and `Inconclusive`. `Fail` (a defect in the system under test) is human-owned. |
| P6 | **Bounded loops** | Every agent loop has a hard iteration cap (default 5), a wall-clock budget, and a token budget. Exceeding any → stop with a report, never retry silently. |
| P7 | **Human review** | Agent output is a patch/PR plus explanation. Nothing is merged or committed to a protected branch by an agent. |
| P8 | **Audit trail** | Every agent action is emitted as `agent.*` events into the same schema-versioned JSON Lines stream as test runs, so renderers/dashboards/regulated customers get one timeline. |
| P9 | **Secrets never enter prompts** | Only `${secret:...}` references appear in specs and in model context. Resolved values are redacted at the tool boundary. |
| P10 | **Provider-agnostic models, on-prem capable** | Model provider is configuration (Azure OpenAI default; OpenAI, Anthropic, Bedrock, Gemini, Ollama/local endpoints via Microsoft Agent Framework). No tool or agent hard-codes a provider. |
| P11 | **One tool contract, two consumers** | vouchfx's own agents consume the **same MCP tools** as external hosts. No private side-channel APIs for the agents. |
| P12 | **Same suite everywhere** | Topological parity is preserved: nothing in this layer depends on where the environment runs (laptop, CI, on-prem Kubernetes). |

## 4. Common conventions for the MCP surface

### 4.1 Transport

- **stdio** (default): for local hosts (Claude Code, Copilot, Cursor, VS Code). Launched as `vouchfx mcp` (existing command or add it) with `--workspace <path>`.
- **Streamable HTTP** (optional, feature-flagged): for CI runners and the hosted `vouchfx-mcp.vouchfx.io` instance. Bearer token auth; no anonymous write tools.
- Use the official **MCP C# SDK** (`ModelContextProtocol` NuGet). Keep the SDK version pinned; the server must declare `protocolVersion` and its `serverInfo.version` = vouchfx package version.

### 4.2 Workspace

All tools operate relative to a **workspace**:

```ts
interface Workspace {
  root: string;              // absolute path; resolved at server start or per-call override
  specsDir: string;          // default: "<root>/e2e" (configurable via vouchfx.config.json)
  outputDir: string;         // default: "<root>/.vouchfx/runs"
  configPath?: string;       // vouchfx.config.json if present
}
```

Path rules: every path parameter is validated to be **inside** `root` after canonicalization (no symlink escape, no `..`). Violations → `VFX-E-1001 PathOutsideWorkspace`.

### 4.3 Versioning

- Every tool result carries `schemaVersion` (DSL schema version the server supports) and `serverVersion`.
- Tool input/output models are additive-only within 1.x. Breaking changes → new tool name with suffix (`_v2`).

### 4.4 Error model

All tool errors are returned as MCP tool errors (`isError: true`) whose content is a single JSON object:

```ts
interface VfxError {
  code: string;              // "VFX-E-1001"
  message: string;           // human-readable, one line
  details?: object;          // structured, tool-specific
  docsUrl?: string;          // https://vouchfx.io/docs/errors/VFX-E-1001
  retryable: boolean;
}
```

Reserved code ranges:

| Range | Area |
|-------|------|
| 1000–1099 | Workspace / path / config |
| 1100–1199 | Schema validation |
| 1200–1299 | Semantic validation |
| 1300–1399 | Compilation |
| 1400–1499 | Orchestration / environment |
| 1500–1599 | Execution / run lifecycle |
| 1600–1699 | Analysis (topology / impact) |
| 1700–1799 | Agent layer |
| 1900–1999 | Internal / unexpected |

Diagnostics (validation/compile) are **not** errors: they are returned as data (`ok: false`, `diagnostics: [...]`) so hosts can iterate. Errors are reserved for "the call itself could not be performed".

### 4.5 Limits & pagination

- Any list-returning tool accepts `limit` (default 200, max 2000) and `cursor` (opaque string) and returns `nextCursor`.
- Text payloads (logs, YAML, CSX) are capped at 256 KB per response; larger → truncated with `truncated: true` and a `resourceUri` to fetch the full artifact.
- Container log tails default to 200 lines, max 5000.

### 4.6 Concurrency & idempotency

- Runs are serialized **per workspace** with a file lock (`<outputDir>/.lock`). A second `run_scenario` while one is active → `VFX-E-1501 RunInProgress` including the active `runId` (retryable: true).
- Read-only tools are safe to call concurrently.
- `write_spec` is idempotent for identical content (returns `changed: false`).

### 4.7 Long-running operations

`run_scenario` may take minutes (container pulls, health gates). Two modes:

1. **Blocking**: `wait: true` (default) with `timeoutSeconds` (default 900, max 3600). On timeout the run continues; the tool returns `status: "running"` + `runId`.
2. **Async**: `wait: false` returns immediately with `runId`; poll via `get_run_status`; cancel via `cancel_run`.

If the pinned MCP SDK supports the **MCP Tasks extension (2026-07-28)** for long-running calls, implement it behind a feature flag in addition to (not instead of) the polling API.

### 4.8 Security

- No tool executes arbitrary shell. `script.csharp` steps remain engine-owned and sandbox-less by design (compile-time providers); the MCP layer adds **no** new dynamic loading.
- `write_spec` refuses content containing secret **literals** (heuristics: connection strings with passwords, `AKIA…`, `-----BEGIN`, long high-entropy tokens) → `VFX-E-1210 SecretLiteralInSpec`; the message tells the caller to use `${secret:...}`.
- Redaction: every log/verdict/env payload passes through the engine's existing redactor before leaving the server.
- Network: the MCP server never calls a model provider. Only `Vouchfx.Ai` does, and only to the configured endpoint.

### 4.9 Observability

- The MCP server emits OpenTelemetry spans per tool call (`vouchfx.mcp.tool/<name>`), with `workspace.hash`, `runId`, duration, outcome. No spec contents or logs in span attributes.
- Server-side structured logs (JSON) with the same correlation ids as the run's JSON Lines stream.

## 5. MCP tool contracts

Naming: tools are exposed as `vouchfx.<verb>_<noun>` (host-visible name `vouchfx.validate_spec`, etc.). Descriptions must be written for a model reader: one sentence on purpose, one on when to call it, one on what to call next. All models below are TypeScript-style for brevity; implement as C# records with `System.Text.Json` source generation and emit JSON Schema for each input (the MCP SDK does this from attributes).

Shared types:

```ts
type VerdictOutcome = "Pass" | "Fail" | "EnvironmentError" | "Inconclusive";   // engine taxonomy, unchanged

interface Location { file: string; line: number; column: number; endLine?: number; endColumn?: number; }

interface Diagnostic {
  code: string;                // "VFX-D-1102"
  severity: "error" | "warning" | "info";
  message: string;
  location?: Location;
  path?: string;               // JSONPath/YAML path into the spec, e.g. "$.steps[2].match.key"
  fix?: { description: string; replacement?: string; };   // machine-applicable when `replacement` is present
  docsUrl?: string;
}

interface ToolMeta { schemaVersion: string; serverVersion: string; workspaceRoot: string; }
```

Every tool result includes `meta: ToolMeta`.

### 5.1 `vouchfx.get_schema`

**Purpose:** Return the DSL JSON Schema (or a section of it) so a host can author valid YAML. **Call first** when authoring.

```ts
interface GetSchemaInput {
  section?: "full" | "metadata" | "environment" | "variables" | "steps" | "step:<family>.<provider>";  // default "full"
  format?: "json-schema" | "summary";   // "summary": compact, model-friendly field list with one-line docs
}
interface GetSchemaOutput {
  meta: ToolMeta;
  schemaVersion: string;
  section: string;
  jsonSchema?: object;
  summary?: string;                     // markdown, ≤ 8 KB
}
```

Notes: `summary` is generated from the schema `description`/`x-vouchfx-doc` annotations. If the schema lacks annotations for a field, add them (additive). This is where most authoring quality comes from — invest here.

### 5.2 `vouchfx.list_providers`

```ts
interface ListProvidersInput { family?: string; includeCommunity?: boolean; /* default true */ }

```

### 5.3 `vouchfx.get_topology`

**Purpose:** Extract a deterministic model of the system under test from the workspace (services, dependencies, contracts, message flows). Authoring and impact analysis depend on it.

```ts
interface GetTopologyInput {
  refresh?: boolean;                    // ignore cache (default false)
  sources?: ("aspire" | "compose" | "openapi" | "avro" | "protobuf" | "asyncapi" | "config" | "existingSpecs")[];  // default: all
  maxDepth?: number;                    // directory scan depth, default 6
}
interface Topology {
  generatedAt: string;                  // ISO-8601
  confidence: "high" | "medium" | "low";
  sources: { kind: string; path: string; }[];
  services: Service[];
  dependencies: Dependency[];
  contracts: Contract[];
  flows: Flow[];                        // inferred producer→consumer edges (Section 8.1)
  warnings: string[];
}
interface Service {
  id: string;                           // "orders-api" (stable, derived from Aspire resource name or compose service)
  image?: string;
  language?: "dotnet" | "java" | "python" | "node" | "go" | "unknown";
  endpoints: { name: string; scheme: "http" | "https" | "grpc"; port?: number; }[];
  env: { name: string; valueRef: string; }[];   // values redacted/referenced, never literal secrets
  sourceRefs: string[];                 // files this was derived from
}
interface Dependency {
  id: string;                           // "orders-db"
  type: "postgres" | "mysql" | "sqlserver" | "mongodb" | "dynamodb" | "kafka" | "rabbitmq" | "nats" | "asb" | "redis" | "elasticsearch" | "s3" | "smtp" | "prometheus" | "otlp" | "other";
  version?: string;
  options?: object;                     // e.g. { schemaRegistry: true }
  consumers: string[];                  // service ids
}
interface Contract {
  id: string;
  kind: "openapi" | "avro" | "protobuf" | "asyncapi" | "sql-schema" | "webhook";
  owner?: string;                       // service id
  path: string;                         // file path
  operations?: { id: string; method?: string; path?: string; topic?: string; requestSchema?: string; responseSchema?: string; }[];
  schemas?: { name: string; fields: { name: string; type: string; required: boolean; }[]; }[];
}
interface Flow {
  id: string;                           // "orders-api:POST /api/v1/users -> kafka:billing.accounts -> postgres:accounts"
  steps: { kind: "http" | "publish" | "consume" | "db" | "webhook" | "cache" | "mail"; ref: string; }[];
  evidence: string[];                   // why we think this flow exists (file:line references)
  confidence: "high" | "medium" | "low";
}
interface GetTopologyOutput { meta: ToolMeta; topology: Topology; cached: boolean; }
```

Cache: `<outputDir>/topology.json` keyed by a hash of the scanned files' mtimes/contents.

### 5.4 `vouchfx.suggest_scenarios`

**Purpose:** Deterministic, heuristic scenario **skeletons** derived from `flows` — a starting point for authoring. Not a model call.

```ts
interface SuggestScenariosInput { flowIds?: string[]; maxSuggestions?: number; /* default 10 */ }
interface ScenarioSuggestion {
  flowId: string;
  title: string;                        // "New user provisioning publishes billing event and projects account"
  rationale: string;                    // one paragraph, cites evidence
  skeletonYaml: string;                 // valid against schema; placeholders marked `TODO_<hint>` in comments only, never in values
  coverage: { services: string[]; dependencies: string[]; stepTypes: string[]; };
  gaps: string[];                       // "request body for POST /users unknown — inspect OpenAPI requestSchema 'CreateUser'"
}
interface SuggestScenariosOutput { meta: ToolMeta; suggestions: ScenarioSuggestion[]; }
```

Skeleton rules: every skeleton must pass `validate_spec` **structurally** (schema) even if semantically incomplete; incomplete parts are expressed as comments and `variables` with obvious names (e.g. `basePath`), not invalid YAML.

### 5.5 `vouchfx.validate_spec`

**Purpose:** Validate a spec (path or inline YAML) against the JSON Schema **and** semantic rules. Returns diagnostics as data. Call after every edit; loop until `ok: true`.

```ts
interface ValidateSpecInput {
  path?: string;                        // relative to workspace root
  yaml?: string;                        // inline; exactly one of path|yaml
  level?: "schema" | "semantic" | "full";   // default "full"
  topology?: "workspace" | "none";      // cross-check targets/topics against get_topology (default "workspace")
}
interface ValidateSpecOutput {
  meta: ToolMeta;
  ok: boolean;
  diagnostics: Diagnostic[];
  normalizedYaml?: string;              // canonical formatting (stable key order, quoting) — hosts should write this back
  summary: { steps: number; stepTypes: string[]; services: string[]; dependencies: string[]; captures: string[]; placeholders: string[]; };
}
```

Semantic rules (implement in `Vouchfx.Analysis.Authoring`; each has a code and a test):

| Code | Rule |
|------|------|
| VFX-D-1201 | Unknown step type (not in registry) — suggest closest by Levenshtein |
| VFX-D-1202 | `target` references a service/dependency not declared in `environment` |
| VFX-D-1203 | `{placeholder}` used before any `capture` or `variables` definition provides it (order-aware) |
| VFX-D-1204 | `capture` defines a name never used (warning) |
| VFX-D-1205 | Step type requires a dependency type absent from `environment.dependencies` (e.g. `mq-expect.kafka` without a `kafka` dependency) |
| VFX-D-1206 | `verifyMode: RETRY` without `timeout` (warning: default applies) / `timeout` above policy max |
| VFX-D-1207 | Secret literal detected → error (see 4.8) |
| VFX-D-1208 | Duplicate step `id` |
| VFX-D-1209 | Asynchronous step type (`mq-expect.*`, `db-assert.*` after a publish, `webhook-listen.*`) without `verifyMode: RETRY` (warning with fix) |
| VFX-D-1210 | Topology cross-check: topic/path/table not found in extracted contracts (warning; `topology: "none"` disables) |
| VFX-D-1211 | `metadata.owner`/`tags` missing (info) |

### 5.6 `vouchfx.compile_spec`

**Purpose:** Compile (YAML → AST → CSX → Roslyn) **without running**. Surfaces compiler diagnostics and optionally the generated CSX for inspection.

```ts
interface CompileSpecInput { path?: string; yaml?: string; emitCsx?: boolean; /* default false */ }
interface CompileSpecOutput {
  meta: ToolMeta;
  ok: boolean;
  diagnostics: Diagnostic[];            // Roslyn diagnostics mapped back to YAML locations where the AST has source spans; else CSX locations
  csx?: string;                         // ≤ 256 KB, truncated flag otherwise
  compilationId?: string;               // handle reusable by run_scenario within the session (optional optimization)
  timings: { parseMs: number; lowerMs: number; compileMs: number; };
}
```

Must reuse the engine's compile path exactly (compile-once discipline). Must `Unload()` the collectible context after compile-only calls; add this path to the memory-leak regression suite.

### 5.7 `vouchfx.run_scenario`

**Purpose:** Orchestrate the topology and execute one or more specs. Returns a run handle and verdict summary.

```ts
interface RunScenarioInput {
  paths: string[];                      // one or more .e2e.yaml (glob allowed, workspace-relative)
  tags?: string[];                      // filter by metadata.tags
  wait?: boolean;                       // default true
  timeoutSeconds?: number;              // default 900, max 3600
  keepEnvironment?: boolean;            // default false — leave containers up for debugging (auto-teardown after 30 min)
  runner?: string;                      // engine runner selection, if the engine exposes it
  labels?: Record<string,string>;       // free-form, recorded in the run (e.g. { "trigger": "agent:author", "iteration": "3" })
}
interface StepResult {
  stepId: string; stepType: string; outcome: VerdictOutcome;
  attempts: number; durationMs: number;
  message?: string;                     // redacted
  captured?: Record<string,string>;     // redacted
}
interface RunSummary {
  runId: string;
  status: "queued" | "running" | "completed" | "cancelled" | "timeout";
  outcome?: VerdictOutcome;             // overall, per engine rules (Fail dominates; EnvironmentError before Inconclusive)
  startedAt: string; finishedAt?: string;
  specs: { path: string; outcome?: VerdictOutcome; steps: StepResult[]; }[];
  environment: { services: string[]; dependencies: string[]; healthGateMs?: number; };
  artifacts: { eventsJsonl: string; htmlReport?: string; junitXml?: string; logsDir?: string; };   // workspace-relative
}
interface RunScenarioOutput { meta: ToolMeta; run: RunSummary; }
```

Behavior: refuses to run a spec that fails `validate_spec` at level `schema` (semantic warnings are allowed) → `VFX-E-1101`. Records `labels` into the JSON Lines run envelope. Emits `run.started` / `run.finished` events.

### 5.9 `vouchfx.get_verdict`

**Purpose:** Full verdict for a run, including per-step outcome reasons, in a shape designed for a model to reason about ("what failed, where, why").

```ts
interface GetVerdictInput { runId: string; specPath?: string; }
interface VerdictDetail {
  runId: string; outcome: VerdictOutcome;
  specs: {
    path: string; outcome: VerdictOutcome;
    steps: (StepResult & {

      relatedLogs?: { container: string; resourceUri: string; }[];

```

`classificationHints` come from `Vouchfx.Analysis.Verdicts` rules (Section 8.3) — they are what make the Healer reliable.

### 5.10 `vouchfx.get_step_timeline`

**Purpose:** The RETRY timeline for one step (every attempt with timestamp, delay, observed value), rendered from the JSON Lines stream without re-running.


## 7. MCP prompts

Prompts are reusable, parameterized instructions that a host can invoke. They encode the *method*, so that any host agent behaves like vouchfx's own Author/Healer. Keep them in `Vouchfx.Mcp/Prompts/*.md` with front-matter for arguments; unit-test that they render.

### 7.1 `author_scenario`

Arguments: `flowDescription` (string, required) · `flowId` (optional) · `specPath` (optional target path) · `constraints` (optional, e.g. "only Core providers", "max 8 steps").

Rendered instruction (abridged; the full text lives in the repo):

> You are authoring a vouchfx `.e2e.yaml` scenario. Follow this procedure exactly and do not skip steps:
> 1. Call `get_schema` (format: summary) and read `vouchfx://docs/dsl-guide`.
> 2. Call `get_topology`; if `confidence` is low, say so and ask for the missing contract instead of guessing.
> 3. Call `suggest_scenarios` for the flow; start from the skeleton, never from a blank file.
> 4. Call `list_providers` for each step type you intend to use; copy parameter names from the registry, never from memory.
> 5. Write the YAML. Use `capture` + `{placeholder}` to thread ids. Every asynchronous assertion uses `verifyMode: RETRY` with an explicit `timeout`. Secrets are `${secret:...}` references only.
> 6. Call `validate_spec` (level: full). Fix **every** error and address warnings; loop until `ok: true`. Maximum 5 iterations; if still failing, stop and report the diagnostics verbatim.
> 7. Call `compile_spec`. Fix compile diagnostics the same way.
> 8. Call `write_spec` with `normalize: true`.
> 9. Call `run_scenario` (wait: true). Then `get_verdict`.
> 10. Interpret the outcome by taxonomy: `Pass` → done, summarize coverage. `EnvironmentError` → check `classificationHints` and `get_run_artifacts`; fix environment declarations only. `Inconclusive` → inspect `get_step_timeline`; adjust `timeout`/`match` only if the observed data shows the assertion is wrong, otherwise report. `Fail` → **do not change the assertion to make it pass**; report the defect with expected/actual.
> 11. Final answer: path written, outcome, what the scenario proves, what it does not cover, open questions.

### 7.2 `heal_run`

Arguments: `runId` (required) · `allowedScopes` (default `["environment","timeouts","match"]`).

> You are diagnosing a vouchfx run that ended in `EnvironmentError` or `Inconclusive`. You must **not** act on `Fail` outcomes except to explain them. Procedure: `get_verdict` → for each non-Pass step read `classificationHints`, `get_step_timeline`, `get_run_artifacts(logs)` → propose the smallest change **inside the spec** (environment declarations, timeouts, match keys, capture paths) or **outside the spec** (image tag, missing dependency, credentials) → if inside the spec: apply via `write_spec(overwrite: true)`, re-run once, compare → produce a report: root cause, evidence (quote log lines), change made or recommended, confidence.

### 7.3 `review_spec`

Arguments: `path`.

> Review this spec for: assertions that cannot fail (tautologies), missing RETRY on async steps, hard-coded ids, missing negative path, coverage gaps against `get_topology` flows, unused captures, secret literals. Output a checklist with severity and concrete edits.

### 7.4 `explain_failure`

Arguments: `runId`, `stepId`.

> Explain to a developer unfamiliar with vouchfx what this step attempted, what it observed (from the timeline), and what the outcome means by taxonomy, in ≤ 200 words.

## 8. Deterministic analysis libraries

### 8.1 `Vouchfx.Analysis.Topology`

**Inputs scanned (in priority order; later sources only add, never override higher-priority facts):**

1. **Aspire AppHost** (`*.AppHost/Program.cs`, `AppHost.cs`): parse with Roslyn (syntax-level, no execution) for `AddProject/AddContainer/AddPostgres/AddKafka/AddRabbitMQ/AddRedis/AddSqlServer/AddMongoDB/...`, `.WithReference(...)`, `.WithEnvironment(...)`, `.WithHttpEndpoint(...)`. Resource names → `Service.id` / `Dependency.id`. `WithReference` edges → `Dependency.consumers`.
2. **docker-compose** (`compose*.y*ml`, `docker-compose*.y*ml`): services, images, ports, `depends_on`, env keys. Dependency type inferred from image name (`postgres:`, `confluentinc/cp-kafka`, `rabbitmq:`, `nats:`, `redis:`, `mcr.microsoft.com/mssql/server`, `mongo:`, `amazon/dynamodb-local`, `elasticsearch:`, `minio/minio`, `axllent/mailpit`, `prom/prometheus`, `otel/opentelemetry-collector`).
3. **OpenAPI** (`openapi*.{json,yaml}`, `swagger*.json`, `**/*.openapi.*`): operations, request/response schema names + fields. Owner inferred by directory proximity to a service's source.
4. **Avro** (`*.avsc`), **Protobuf** (`*.proto`), **AsyncAPI** (`asyncapi*.y*ml`): schemas/fields; topics from AsyncAPI channels or from naming conventions in config (see 5).
5. **Config**: `appsettings*.json`, `application*.{yml,properties}`, `.env*`, `config/*.{yaml,toml}` — extract topic/queue names via keys matching `/(topic|queue|subject|channel)/i`; DB connection *presence* (never values); base paths.
6. **Existing specs** under `specsDir`: their `environment` blocks are authoritative for ids already in use (keeps ids stable across runs).
7. **Source heuristics** (lowest confidence, feature-flagged): .NET `ProduceAsync("topic")`, `Subscribe("topic")`; Java `@KafkaListener(topics=...)`, `kafkaTemplate.send("...")`; Python `producer.send("...")`; Node `producer.send({ topic: ... })`. Regex-based; each hit recorded as evidence with `file:line`.

**Flow inference:** for each HTTP operation of service S, if S's source or config mentions a topic T and a dependency D of type message broker exists, add edge `http → publish(T)`; for each service C consuming T (listener evidence) with a DB dependency, add `consume(T) → db`. Flows are ranked by evidence count. Confidence: high = Aspire/AsyncAPI/OpenAPI-backed; medium = compose/config; low = source heuristics only.

**Output:** `Topology` (Section 5.3). Cache as described. Unit tests: fixtures from all four `vouchfx-samples` apps must produce the expected services/dependencies/flows (golden JSON).

### 8.2 `Vouchfx.Analysis.Impact`

**Reference extraction from specs** (per step, by family):

| Family | References extracted |
|--------|----------------------|
| http.* | `target`, `method`, `path` (with placeholders normalized to `{*}`), body schema hints (top-level keys), `capture` JSONPaths |
| mq-publish.* / mq-expect.* | `topic`/`queue`/`subject`, `match.key`, schema registry subject if present, message top-level keys |
| db-assert.* | `target`, table names from `query` (simple SQL tokenizer: `FROM`, `JOIN`, `UPDATE`, `INSERT INTO`), column names in `WHERE`/`SELECT` |
| cache-assert.* | key patterns |
| webhook-listen.* | path, expected payload keys |
| environment | service ids, images, dependency ids/types/versions |

**Contract diffing:**

- OpenAPI: operations added/removed/renamed (path template equality), method changes, request/response schema field removed/renamed/type-changed/required-added.
- Avro/Protobuf/AsyncAPI: fields removed/renamed/type-changed, topics/channels renamed/removed, schema version bumps.
- Aspire/compose: service renamed/removed, image changed, dependency type/version changed, env key removed.
- SQL schema (`*.sql` migrations, EF migrations): table/column drops and renames (best effort; flag as medium confidence).

**Matching → `ImpactedStep`:** a step is impacted if any of its references intersects a changed contract element. `reasons[].code` reuse the `changes[].type` vocabulary. Confidence: high when the reference is exact (topic string equality); medium when path templates matched with wildcards; low when only body/top-level key overlap.

**`suggestedSpecEdits`** only for *mechanical* renames (topic renamed A→B, path renamed, service id renamed) with unambiguous 1:1 mapping. Everything else goes to `unknowns`.

**`suggestedRun`:** all impacted specs plus any spec sharing an `environment.services` image that changed.

### 8.3 `Vouchfx.Analysis.Verdicts`

Reader over the schema-versioned JSON Lines stream (reuse the engine's event envelope types; do not redefine). Produces `VerdictDetail`, `Attempt[]` timelines, and `classificationHints` via a rule table (each rule: match on event type/fields → hint text + `reason.kind`). Initial rules:

| Signal | Kind | Hint |
|--------|------|------|
| image pull error / manifest unknown | pull | "Image tag likely wrong or registry auth missing: <image>" |
| health gate timeout for resource R | unhealthy | "Resource R never became healthy within <ms>; check its logs (resourceUri)" |
| seed step failed | seed | "Seeding failed on <target>: <error>" |
| RETRY exhausted, observed values non-empty | timeout | "Observed <n> messages on <topic> but none matched key <key>; the key or capture path is probably wrong" |
| RETRY exhausted, observed values empty | timeout | "No messages observed on <topic> at all; producer path, topic name or serialization is the likely cause" |
| capture unmet | capture_unmet | "Step <id> captured nothing at <jsonpath>; response shape differs from expectation" |
| partition/grace exceeded | partition | engine text |
| assertion mismatch with both values present | assertion | "Expected <e>, actual <a>" |
| Roslyn diagnostic | compile | mapped to YAML location |

Hints are plain strings + the structured `reason`; both are tested.

### 8.4 `Vouchfx.Analysis.Authoring`

- Semantic validation rules VFX-D-1201…1211 (Section 5.5).
- YAML normalizer (stable key order per schema; quoting rules; comment preservation via a YAML CST library — if comment preservation is impractical, document that `normalize` drops comments and default it to `false`).
- Skeleton generator for `suggest_scenarios` (Section 5.4): templates per flow shape (`http→publish→db`, `http→db`, `publish→consume→db`, `http→webhook`), filled from topology; emits comments for gaps.
- Secret-literal heuristics (shared with `write_spec`).

## 9. Agent layer — `Vouchfx.Ai` on Microsoft Agent Framework

### 9.1 Stack

- **Microsoft Agent Framework 1.0** (.NET packages under `Microsoft.Agents.AI.*`; GA April 2026, LTS). Use: `ChatClientAgent`/agent abstractions, function tools, **MCP client** integration (agents call the vouchfx MCP server tools — P11), middleware (for budgets/audit), OpenTelemetry integration, and the sequential orchestration pattern for Author→Healer handoff.
- **MCP connection**: default **in-process** host of `Vouchfx.Mcp` (same process, no stdio) for CLI runs; `--mcp stdio|http <url>` to attach to an external server (e.g., CI runner). Either way the agents see the identical tool surface.
- **Model providers** via Agent Framework connectors: Azure OpenAI (default), OpenAI, Anthropic, Amazon Bedrock, Google Gemini, Ollama/OpenAI-compatible local endpoints. Selection is configuration only (`VOUCHFX_AI_PROVIDER`, `VOUCHFX_AI_MODEL`, `VOUCHFX_AI_ENDPOINT`, `VOUCHFX_AI_API_KEY` or managed identity). **On-prem**: Ollama/Foundry Local/private Azure endpoint; no code differences.
- Do not depend on Agent Harness or Foundry Hosted Agents in this phase.

### 9.2 Configuration (`vouchfx.ai.json` in workspace root, env vars override)

```json
{
  "provider": "azure-openai",
  "model": "gpt-5",                       // any chat model the provider exposes; leave to user
  "endpoint": "https://<resource>.openai.azure.com",
  "auth": "managed-identity | api-key",
  "budgets": { "maxIterations": 5, "maxWallClockSeconds": 1800, "maxInputTokens": 400000, "maxOutputTokens": 60000, "maxRuns": 6 },
  "scopes": { "author": ["write_spec","run_scenario"], "heal": ["environment","timeouts","match"], "impact": ["suggest"] },
  "audit": { "eventsPath": ".vouchfx/runs/agent-events.jsonl", "includeToolPayloads": false },
  "redaction": { "extraPatterns": [] }
}
```

Budgets are enforced by **middleware** around the agent loop: every tool call and model call decrements; exhaustion → `VFX-E-1701 BudgetExceeded` with a report of what was achieved. Never silent.

### 9.3 Agents

#### 9.3.1 Author agent — `vouchfx ai author`

```
vouchfx ai author --flow "New customer is provisioned end-to-end" [--flow-id <id>] [--out e2e/provision-customer.e2e.yaml] [--constraints "core-only,max-steps=8"] [--no-run] [--pr]
```

System prompt = the `author_scenario` MCP prompt (Section 7.1) + workspace context (`vouchfx://docs/dsl-guide`, `vouchfx://workspace/specs` index). Tool allowlist: `get_schema, list_providers, get_topology, suggest_scenarios, validate_spec, compile_spec, write_spec, run_scenario, get_run_status, get_verdict, get_step_timeline, get_run_artifacts, explain_diagnostic`. **No** file tools, **no** shell.

Loop (implemented as explicit orchestration code, not left to the model):

```
topology := get_topology
skeleton := suggest_scenarios(flow) or empty template
for i in 1..maxIterations:
    yaml := model.propose(yaml, diagnostics, hints)         # model turn with tools available
    v := validate_spec(yaml, full)
    if !v.ok: diagnostics := v.diagnostics; continue
    c := compile_spec(yaml)
    if !c.ok: diagnostics := c.diagnostics; continue
    write_spec(out, v.normalizedYaml, overwrite=(i>1))
    if --no-run: break
    run := run_scenario([out]); verdict := get_verdict(run.runId)
    switch verdict.outcome:
        Pass:              break
        EnvironmentError:  hints := verdict.classificationHints; allow edits to environment.* only; continue
        Inconclusive:      hints := timelines; allow edits to timeout/match/capture only; continue
        Fail:              break   # never edit assertions to pass; report the defect
emit report (markdown + JSON); if --pr: create branch + PR via `gh` if available, else print patch
```

Output: `AuthorReport { specPath, iterations, finalOutcome, coverage, notCovered[], openQuestions[], runIds[], tokenUsage, patch }`.

#### 9.3.2 Healer agent — `vouchfx ai heal`

```
vouchfx ai heal --run <runId> [--scopes environment,timeouts,match] [--apply] [--pr]
```

Precondition: run outcome ∈ {`EnvironmentError`, `Inconclusive`}. If `Fail` → exits 0 with an explanation report and **no changes** (`VFX-E-1702 HealerRefusesFail` is logged as an info event, not an error). Tool allowlist: `get_verdict, get_step_timeline, get_run_events, get_run_artifacts, get_topology, validate_spec, compile_spec, write_spec (only with --apply), run_scenario (max 1 re-run), explain_diagnostic`.

Procedure = `heal_run` prompt. Output: `HealReport { runId, rootCause, evidence[], change: { location: "spec" | "external", diff?, recommendation? }, rerun?: { runId, outcome }, confidence }`.

#### 9.3.3 Impact agent — `vouchfx ai impact`

```
vouchfx ai impact --base main [--head HEAD] [--apply-mechanical] [--comment-pr]
```

Step 1 is **deterministic**: `impact_of_contract_change(kind: git)`. The model is invoked **only** for `report.unknowns` (e.g., "field `customerId` renamed to `clientId` in `CreateUser` — does step `create-user.capture.newUserId` need `$.clientId`?") with tools `validate_spec, compile_spec, write_spec(--apply only), get_topology`. If `unknowns` is empty, no model call is made at all (log it). Output: `ImpactReport` + proposed edits + `suggestedRun`, and a PR comment (GitHub Action) listing impacted scenarios with reasons.

### 9.4 Audit events (appended to the same JSON Lines stream as runs; schema-versioned)

```ts
type AgentEvent =
  | { type: "agent.session.started"; agent: "author"|"heal"|"impact"; sessionId: string; workspaceHash: string; provider: string; model: string; budgets: object; at: string; }
  | { type: "agent.model.call"; sessionId: string; iteration: number; inputTokens: number; outputTokens: number; durationMs: number; at: string; }   // never the content
  | { type: "agent.tool.call"; sessionId: string; iteration: number; tool: string; argsHash: string; ok: boolean; durationMs: number; errorCode?: string; at: string; }
  | { type: "agent.spec.written"; sessionId: string; path: string; contentHash: string; iteration: number; at: string; }
  | { type: "agent.run.linked"; sessionId: string; runId: string; iteration: number; at: string; }
  | { type: "agent.decision"; sessionId: string; kind: "stop_pass"|"stop_fail_reported"|"stop_budget"|"stop_max_iterations"|"refused_fail"|"continue"; reason: string; at: string; }
  | { type: "agent.session.finished"; sessionId: string; outcome: string; reportPath: string; at: string; };
```

`includeToolPayloads: true` additionally stores redacted tool args/results under `.vouchfx/runs/agent-payloads/<sessionId>/` for regulated customers who need full reproducibility.

### 9.5 Telemetry

OpenTelemetry via the Agent Framework's built-in instrumentation + vouchfx spans; exported only if the user configures an OTLP endpoint. No default remote telemetry. The existing `telemetry.vouchfx.io` backend, if used, must be explicit opt-in with a documented data list.

### 9.6 GitHub Action (`Vouchfx.Ai.GitHubAction`)

`action.yml` inputs: `command` (`author|heal|impact`), `workspace`, `provider`, `model`, `endpoint`, `api-key` (secret), `base-ref`, `apply` (bool), `comment-pr` (bool). Runs the `vouchfx` and `vouchfx.ai` dotnet tools in a container with Docker socket access (needed by Aspire/Testcontainers). Publishes the JUnit XML as a check and the agent report as a job summary. Never pushes to the PR branch unless `apply: true` **and** the workflow grants `contents: write`.

### 9.7 Safety rules (hard; test each)

1. Agents can only write via `write_spec`; `write_spec` only writes `*.e2e.yaml` under `specsDir`.
2. Healer never modifies a spec whose run outcome is `Fail`; Author never changes an assertion after a `Fail` to make it pass.
3. Every loop terminates by `maxIterations`, wall-clock, token budget, or `maxRuns` — whichever first — with a report.
4. Secret literals are rejected at `write_spec` and stripped from any model context (validate before sending to the model).
5. No network egress from agents except the configured model endpoint (and `gh` when `--pr`).
6. No agent action mutates git history on protected branches; PR creation is opt-in.
7. All agent decisions are logged as `agent.decision` events.
