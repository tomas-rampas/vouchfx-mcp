# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A local, stdio-first MCP (Model Context Protocol) server — with an optional, flag-gated HTTP transport — written in C# / .NET 8, that wraps the **published `vouchfx` dotnet tool** as a subprocess — it never builds the engine from source and never re-implements engine logic in-process ("CLI and MCP must not drift" is the governing invariant). It ships **eighteen tools, four prompts and eleven resources**, packaged as the `Vouchfx.Mcp` dotnet tool (command `vouchfx-mcp`), not yet published to NuGet.org. The resources split the way the protocol splits them — four CONCRETE on `resources/list` (the two vendored documents, `vouchfx://workspace/specs`, `vouchfx://docs/dsl-guide`) and seven URI TEMPLATES on `resources/templates/list` covering six families (schema versions, the error catalogue under BOTH `vouchfx-docs:///errors/{code}` and its `vouchfx://docs/errors/{code}` alias — two templates, one family — example suites, and the three `vouchfx://runs/{runId}/…` families). The four prompts (`author_scenario`, `heal_run`, `review_spec`, `explain_failure`) are procedures the HOST's model executes over these tools; this server still hosts no model. `SKILL.md` at the repository root is the Claude Code skill that routes a session into them. Sprints 1 (contract foundations: `ToolMeta`, the `VFX-E-####`/`VFX-D-####` taxonomy, `explain_diagnostic`), 2 (authoring quality: `get_schema`, `validate_suite` v2, the VFX-D-1201…1211 semantic rules, `normalize_suite`, catalogue enrichment), 3 (run lifecycle: persisted registry, cross-process lock, six inspection tools), 4 (verdict intelligence: `reason.kind` rule table, Healer spec-edit proposals, measured ladders) and 5 (the host-facing method: the `vouchfx://` resource set, the four prompts, `docs/dsl-guide-for-agents.md`, `SKILL.md`, and the M4 acceptance drill) and 6 (relays and hardening: the ENGINE_PIN repin to v1.0.0-rc.5 plus the YamlDotNet fleet realignment back to the engine's 16.3.0, one bounded `ActivitySource` span per tool call, structured JSON-per-line stderr logging correlated by runId, and the optional `--transport http` mode with bearer auth; the MCP Tasks extension was measured against the pinned SDK and closed **blocked-on-SDK**) of the vouchfx.ai plan have landed on this codebase.

## Commands

```bash
dotnet build Vouchfx.Mcp.sln -c Release -warnaserror   # 0-warning gate (TreatWarningsAsErrors is on anyway)
dotnet test Vouchfx.Mcp.sln -c Release --no-build      # build first: Real* tests spawn the built Vouchfx.Mcp.dll at the same -c
dotnet test tests/Vouchfx.Mcp.Tests/Vouchfx.Mcp.Tests.csproj --filter "FullyQualifiedName~SuiteValidatorTests"   # one class
dotnet test tests/Vouchfx.Mcp.Tests/Vouchfx.Mcp.Tests.csproj --filter "FullyQualifiedName~ClassName.MethodName"  # one test
dotnet format Vouchfx.Mcp.sln --verify-no-changes      # CI format gate; run plain `dotnet format` to fix
dotnet pack src/Vouchfx.Mcp/Vouchfx.Mcp.csproj -c Release -o artifacts/nuget   # tool nupkg (default 0.1.0-alpha.1)
pwsh ./scripts/sync-vendored.ps1 -Verify               # vendored/ drift gate (CI runs this); -Update is the ONLY way to refresh vendored/
python scripts/build_site.py                           # docs site → _site/ (needs markdown, pygments, vouchfx-site-tools)
```

SDK: .NET 8 (`global.json`: 8.0.400, rollForward latestFeature). Shared MSBuild properties live in the root `Directory.Build.props` (net8.0, nullable, warnings-as-errors, `IsPackable=false` default); per-project files deliberately do not repeat them, and `tests/Directory.Build.props` must keep its explicit import of the root file.

CI (`.github/workflows/build.yml`) runs three parallel jobs: build+format+test, the vendored-drift gate, and a pack job that unzips the nupkg and asserts the tool manifest, `ENGINE_PIN`, and entry DLL are present. `release.yml` does the real tag-versioned pack (`-p:PackageVersion=<semver-from-tag>`).

## Engine pin and vendored artefacts

- **`ENGINE_PIN`** (repo root): first line is `<version> <full-40-char-commit-sha>`. The *version* gates the runtime CLI handshake (`CliPinVerifier` — fail-closed for CLI-dependent tools); the *SHA* is what `vendored/` is drift-gated against in CI. The file ships beside the built exe (a `Content` item); `EnginePin.Load` at startup is fatal if it is missing or malformed. The file's own comment block documents how to advance it — including a real gotcha about annotated vs lightweight tags (use `gh api repos/tomas-rampas/vouchfx/commits/<tag> --jq .sha`).
- **`vendored/`** (composed schema, language reference, recipes): byte-exact copies from the engine repo at the pinned SHA, embedded into the assembly as manifest resources with explicit `LogicalName`s. **Never hand-edit them, and never regenerate the schema via `vouchfx schema`** (CRLF/trailing-newline differences fail the SHA-256 drift gate) — `pwsh ./scripts/sync-vendored.ps1 -Update` is the only supported refresh path. See `vendored/README.md`.

## Architecture

`Program.cs` has THREE top-level branches, checked in this order. (1) Two hidden one-shot WORKER modes, tested before anything else because each owns its own stdout contract: `--validate-worker <source> [--level=<level>] [--normalize]` (the validate_suite / normalize_suite process-isolation boundary; `<source>` is a suite path or `--yaml-stdin`, in which case the suite text arrives on the worker's stdin; `--normalize` selects normalize_suite's canonical-YAML response shape) and `--spec-index-worker` (US-S5-01's per-suite JSON Lines indexer for `vouchfx://workspace/specs`). (2) The TRANSPORT selection (`--transport stdio|http`, US-S6-06), parsed near the top so an HTTP mode with no bearer token fails before any listener could exist. (3) The server itself, over the selected transport. **stdout is the JSON-RPC channel in server mode and nothing else may ever write to it** — everything this server says goes to stderr as ONE JSON OBJECT PER LINE (US-S6-05); tests assert stdout cleanliness on both transports.

`VouchfxMcpServerRegistration.AddVouchfxMcpServer` is the single DI configuration used by both production startup and the test harness — there is no second copy to drift. `Tools/ToolRegistry` aggregates the eighteen tools (append-only ordering — the tool-count lock test updates with every addition); each tool's name/description/input schema is owned by that tool's own `Create()` factory in `Tools/`. Error and diagnostic emissions flow through `Contracts/VfxCodeCatalogue` (the single kind→code registry) — never mint a `VFX-*` code outside it; the bidirectional catalogue completeness gate fails CI on any code without a `docs/errors/` page or page without an emitting site.

The eighteen tools split into five dependency classes (`explain_diagnostic` joins the CLI-free class — it serves the embedded error catalogue and never probes the engine; US-S3-03 added the fifth, which has exactly one member):

- **CLI-free** (work offline, no engine install): `validate_suite` — `Validation/` pipeline (YamlDotNet parse with `YamlSafetyGuard`/`PathSafetyGuard` hardening, YAML→JSON, JsonSchema.Net against the vendored schema), executed in a spawned worker process (`ValidationWorkerClient` — wall-clock timeout, process-tree kill). Takes either a `path` or inline `yaml` (never both) and a `level` selector (`schema`/`semantic`/`full`, default `full`) that gates the passes but never the safety guards; returns two permanently separate channels — `errors` (schema) and `semanticDiagnostics` (this server's own advice) — plus a `summary` digest of the document, all from one parse. `Validation/Semantics/` is the rule seam US-S2-03 fills: a rule gets the parsed document, the caller-facing digest, and `SuiteFacts` (the complete, uncapped, unfiltered name sets — the set-membership authority, never serialised). `normalize_suite` — `Normalization/`, US-S2-04's read-only replacement for the spec's dropped `write_spec`: same worker isolation and same exactly-one-of-`path`/`yaml` rule (VFX-E-1152) as `validate_suite`, always at level `full`, returning `{normalizedYaml, validation}` where `validation` is the whole `SuiteAnalysis` shape. Canonical key order is derived from the vendored schema's own `properties` declarations (`CanonicalKeyOrder`); normalization **drops comments** on the pinned YamlDotNet (measured — see `SuiteNormalizer`'s remarks) and is therefore opt-in behind `normalize: true`. The server never writes the file — the host does. `search_docs` — `Docs/` search over the vendored markdown.
- **Pinned-CLI-backed** (fail closed if `vouchfx` is missing or its version mismatches `ENGINE_PIN`): `list_step_types`/`describe_step_type` (live catalogue via `vouchfx list --json`, `Validation/LiveStepCatalogue`), `plan_coverage` (`Planning/`, `vouchfx plan --json`; since issue #76's close its `path`/`eventsPath` run the full `PathSafetyGuard` chain — UNC refused unconditionally, workspace-contained when configured — closing the one tool that bypassed it), `scaffold_suite` (`Scaffold/`, `vouchfx scaffold --intent`), `run_suite` (`Run/`, takes `path` or `paths` with workspace-relative globs, validates every suite first, spawns the CLI once per suite sequentially, records labels in the registry, streams best-effort progress, returns the taxonomy-faithful verdict; only `wait: true` and `keepEnvironment: false` are implemented; `wait: false` and `keepEnvironment: true` are refused with VFX-E-1504 pending upstream ask U4). The `Cli/` directory holds the shared subprocess plumbing (`VouchfxCliProcessRunner`, `CliPinVerifier`, path resolution, version normalisation).
- **CLI-optional** (never fails for want of an engine, but uses one when present): `get_schema` (`Schema/`) serves the vendored composed schema — whole document or one addressable section, as JSON Schema or an 8 KB markdown digest — entirely offline; when the pinned CLI *is* present (`CliPinVerifier` via `Validation/LiveSchemaDocument`), the embedded copy is cross-verified against that engine's `vouchfx schema` export and any divergence is surfaced as a `VFX-D-1106` diagnostic on the still-successful result. The CLI contributes a check, never the content: the vendored copy is always what gets served, so `get_schema` and `validate_suite` can never disagree.
- **Events-file readers** (never re-run anything, and never take the run lock — spec §4.6's "read-only tools are safe to call concurrently", held structurally by `RunLockSourceGuardTests`): `explain_run` and `diagnose_run` (`Diagnosis/`) parse a run's JSON Lines event stream; `explain_run` defaults to the most recent finished run recorded in the run registry (`IRunRegistry` — spans server restarts when `--workspace` is used, session-scoped otherwise). `diagnose_run` (Healer) adds patch proposals **only for Fail verdicts**; EnvironmentError gets infrastructure guidance, never YAML rewrites; proposals are never auto-applied. `get_run_events` (`Run/`, US-S3-05) is the raw counterpart: it resolves a `runId` through the registry — the one `run_suite`'s own result now carries, which is what makes the hand-off in-band — reads the same file through the same `EventsFileReader`, filters by event `types`/`stepId` **before** paging, and relays the engine's own JSON objects — **wire tokens** (`PASS`/`FAIL`/`ENV_ERROR`/`INCONCLUSIVE`), unknown types and fields intact — through `Run/RawEventRelay` (the second sanitised relay onto that file; there must never be an unsanitised third). Every bound `RawEventRelay` applies is VISIBLE in the output (`_vfxTruncated`, `_vfxStringsCapped`) and every "cannot relay this faithfully" path converges on the truncation marker — including a line carrying an unpaired surrogate escape, which parses and then throws on decode; the result's `truncated` flag separately reports that the SCAN stopped at the 50 MB / 2M-line bounds, which no absent cursor would otherwise reveal. `Run/OpaqueCursor` is THE cursor implementation for the whole server (spec §4.5): base64url, versioned, integrity-checksummed, and bound to the caller's filters so a cursor from a different page walk is refused (VFX-E-1506) rather than misapplied — `list_runs` reuses it verbatim under `CursorScopes.ListRuns`, the shared `OpaqueCursorContract` test fixture is driven from both tools' tests, and `CursorCallSiteSourceGuardTests` pins the encode/decode call sites to exactly those two orchestrators. `get_run_status` and `list_runs` (`Run/GetRunStatusOrchestrator`, `Run/ListRunsOrchestrator`, US-S3-03) are the registry's own read surface: `get_run_status` serialises the `RunRegistryEntry` itself rather than projecting it (AC: "not a second, divergent status model"), and `list_runs` projects spec §5.8's mandated five-field `Pick`, positions its cursor on a **`startedAt` boundary rather than an index** (the registry is re-scanned per page and every new run lands at the head), and since US-S3-06 reports the registry's own scan cap as `truncated` — `IRunRegistry.ListRuns` returns a `RunListing` (an `IReadOnlyList<RunRegistryEntry>` plus a `ScanCapped` bool) precisely because the registry, not the orchestrator, is the party that knows the walk stopped short. `get_step_timeline` (`Run/GetStepTimelineOrchestrator`, US-S3-06) is the fourth reader and the one whose whole purpose is a truncation inversion: `explain_run`'s tiers shrink `notableSteps[].attempts` FIRST (10 → 5 → 0), so this tool keeps every attempt and shrinks per-attempt `observed` text instead (`ObservedCharTiers`, then a measured list-fit as a bounded last resort). It reuses `SuiteEventParser`'s `AttemptsByStepId` rather than re-parsing — the AC is "extracted from, not duplicated alongside" — and two fields of spec §5.10 come back as explicit nulls for two DIFFERENT reasons, while a third that earlier documentation lumped in with them does not: `Attempt.at` IS populated, relayed from the `ts` every event carries (measured, `RealStepAttemptEnvelopeAgainstPinnedCliTests`); `Attempt.delayMs` is STRUCTURALLY null (no event type carries an inter-attempt delay at all); and `timeoutMs` is null as a fact about THIS BUILD only — the engine's `step-started` event carries it, and `SuiteEventParser` does not handle that type (local follow-up #81; widening the shared parse feeds three other tools); the per-attempt `outcome` is the tool's OWN `matched`/`unmatched`/`error` enum, never the verdict taxonomy and never a wire token. Its `specPath` argument is validated against the run's `specPaths` (VFX-E-1509) but cannot filter a multi-suite run — the concatenated stream has no per-suite attribution (US-S3-02's documented trade) — which `specPathAttributed: false` states rather than hides; an unknown `stepId` is VFX-E-1510, deliberately NOT an empty timeline, because a step with no attempt events is a real and different success. `get_run_artifacts` (`Run/GetRunArtifactsOrchestrator`, US-S3-07) is the fifth reader and the sprint's one application of `sprint-00-overview.md` §3's stance **(b)** — a data-returning surface with an upstream-gated portion succeeds with `partial: true` and the derivable subset, never an error and never a fabricated value. Its inventory is short and MEASURED: `reports.events` (the registry's own `eventsFilePath`, with `available` saying whether the file survives) is the only report artefact — the engine's HTML/JUnit paths are omitted, not nulled, because this server is never told them; `logs` is permanently `[]` (no container log access exists at all); and `environment` yields ONLY what an `environment-error` event names (`resourceName`/`errorKind`/`detail` via the shared `SuiteEventParser`), which is why spec §5.12's `services`/`dependencies` stay empty and every identifier lands in an additive `resources` array with `role: "unclassified"` — the event says which resource failed, never which KIND of resource it is, and the suite's own `environment:` block is refused as a source for the same reason `get_step_timeline` refuses to read a suite for `verifyMode`. Every gap is named per field in a `gaps` array (field, reason, `awaits: "U4"`), and `partial` is COMPUTED from that list rather than hardcoded — which is what makes it stance (b)'s varying marker rather than US-S3-06's per-field nulls (the discriminator recorded in `sprint-00-overview.md` §3). It is also the one reader that does NOT map a swept or unreadable events file to VFX-E-1004/1005: for the others that file is the whole answer, here it is one input of three, so it is reported as `available: false` plus a gap. `container` and `tailLines` are accepted and validated (default 200, max 5000, refused-not-clamped) although neither selects nor bounds anything pre-U4, so the contract does not change again when it lands.
- **Lifecycle-mutating** (the one tool that is neither read-only nor a runner): `cancel_run` (`Run/CancelRunOrchestrator`, US-S3-03) owns no stop mechanism — it fires the `CancellationTokenSource` the in-flight run is *already* executing under, published under its runId by `RunSuiteOrchestrator` into the process-local `Run/IRunCancellationRegistry`. That makes AC-002's "no second, divergent cancellation path" structural: downstream it is indistinguishable from the caller's own token firing, so `VouchfxCliSuiteRunner`'s stdin-close → 35 s grace → force-kill sequence and EDGE-002's Inconclusive-never-Fail path both run unchanged. A `cancel_run`-driven stop is the ONLY thing that writes `RunRegistryStatus.Cancelled` (the caller's token and the timeout budget still write `completed`; `timeout` stays unreachable) and it never rewrites the run's **outcome** — the status says how the run ended, the outcome says what it reached. **Cross-process cancel is refused, not faked** (`VFX-E-1507`): the run lock carries no payload, so there is no channel, and a sideband file would be the second path the AC forbids. `cancel_run` is also the *only* permitted second `IRunLock.TryAcquire` call site (`RunLockSourceGuardTests`) — a take-and-release probe distinguishing "another process holds it" from a phantom `running` entry left by a hard-killed server (`VFX-E-1508`), which read-only tools deliberately do not attempt because a momentary claim could make a concurrent `run_suite` fail.

**`Prompts/`** (Sprint 5) is the second primitive, and it is DATA rather than code: four `.md` documents (`author_scenario`, `heal_run`, `review_spec`, `explain_failure`) are embedded as manifest resources and parsed by `PromptDocumentParser` into `PromptDefinition`s, so a prompt's **front matter is the single source of truth** for its name, title, description and argument list — there is no second C# declaration to drift from it, which is the same reason each tool owns its own schema in its `Create()` factory. `PromptTemplate` renders `{{name}}` plus `{{#name}}`/`{{^name}}` sections in ONE pass with sections resolved before values (so a value can never be mistaken for markup), and treats absent and explicitly-empty as different — an omitted argument takes the documented default while an explicitly empty one does not, which is what stopped `heal_run`'s `allowedScopes: []` from meaning "all scopes permitted" (the most restrictive request producing the most permissive text). Parse time enforces **set EQUALITY** between declared arguments and body placeholders in both directions (`PromptDocumentParser`): an undeclared placeholder renders empty and is a silent hole, a declared-but-unused argument is a contract this server does not honour. `PromptRepository.All` is an eager static forced by Program.cs's fourth startup preflight (a malformed prompt must name its file on stderr, not surface as a `TypeInitializationException` from inside the transport). The load-bearing test is `PromptSurfaceCrossCheck`: every tool name, argument name and **argument VALUE** a prompt's procedure text names is checked against the advertised surface — built after two BLOCKERs that presence-only tests could not see (`format: markdown`, which the schema rejects, and a missing `normalize: true`, which silently returned `normalizedYaml: null`).

**`Resources/`** is one registry per family, aggregated by `ResourceRegistry`. Two things there are not obvious. First, the three `vouchfx://runs/{runId}/…` resources are handed the tools' OWN orchestrator instances (`ExplainRunOrchestrator`, `GetRunEventsOrchestrator`, `GetRunArtifactsOrchestrator`) rather than reimplementing anything, and `ResourceJson` serialises through `StructuredToolResult.Options` — the same resolver chain the tool path uses — so "the resource serves the same data as the tool" is checkable byte-for-byte (the goldens assert equality with the tool's `structuredContent` minus its `meta` stamp, which is deliberately the one difference: `meta` is a tool-result field, and stamping it here would be the second stamping site `ToolMeta`'s choke point exists to prevent). Second, `vouchfx://workspace/specs` parses every discovered suite in a **spawned child process** (`--spec-index-worker`, `Specs/SpecIndexWorkerClient`, streaming JSON Lines with a two-allowance budget and a watchdog) — the SECOND process boundary in this codebase and for the identical reason as `validate_suite`'s: a twelve-byte file can drive the YamlDotNet Scanner into an uninterruptible spin that no `CancellationToken` can stop, and the enumeration walks whatever the workspace happens to contain. A suite that cannot be parsed is still LISTED with `readable: false`, because a thin entry and a missing entry are different facts.

**`Observability/`** (Sprint 6, US-S6-04) is the tool-call tracing seam, and it is deliberately the smallest thing that can work: instrumentation is `System.Diagnostics.ActivitySource` and there is **no OpenTelemetry package in the product** — choosing an exporter belongs to whoever runs the process, on both transports: a stdio host spawns this server as a child with no OTLP endpoint and MCP carries no trace context (an exporter would export nothing), while the long-lived `--transport http` deployment could reach a collector but is served just as well by the attach route — without this server owning exporter configuration, credentials, an export loop, or a write path to audit against invariant 11; `StartActivity` returning null with no listener is what makes "a host with no collector sees zero change" a BCL property rather than a claim. Every tool emits exactly one span from the `Vouchfx.Mcp` source named `vouchfx.mcp.tool/<toolName>`, parented under the MCP SDK's own per-request span (measured: the SDK's source is `Experimental.ModelContextProtocol`). Emission happens at ONE interception point — `InstrumentedMcpServerTool`, a `DelegatingMcpServerTool` subclass applied to the whole list inside `ToolRegistry.CreateAll` — so all eighteen tools and every future one are instrumented by existing, and no tool factory knows observability exists. Attributes are bounded to exactly four (`workspace.hash`, `runId`, `duration_ms`, `outcome`) by the shape of `ToolTelemetry`'s API: four typed parameters, no free-form key, no way to reach the `Activity`, `duration_ms` computed rather than accepted, and `runId` shape-gated through `RunRegistryCore.IsWellFormedRunId` because on the argument path it is caller-supplied text. `ToolTelemetrySourceGuardTests` closes the escape hatches structurally (no `ActivitySource` construction, `StartActivity`, `Activity.Current` or `SetTag`/`AddTag` anywhere in `src/` outside the helper).

The same directory holds US-S6-05's **structured logging**, which is the stderr counterpart of that tracing seam and needs no collector at all. `StructuredLog` writes one JSON object per line to stderr — `{timestamp, level, message, runId?, seq?, errorType?}`, UTC round-trip timestamps, optional fields OMITTED rather than nulled — through ONE private writer reached by two entry points: `StructuredConsoleFormatter` for anything logged via `ILogger` — which, since US-S6-06 deleted `Log.cs`, means **Hosting/SDK/Kestrel output only**, whose exception contributes its TYPE NAME only, and nothing this server writes on its own behalf — and direct `Write`/`ForRun` calls for everything this server does say: `Program.cs`'s two startup BANNERS (pin, containment policy — moved above the transport branch so an HTTP operator gets them too, which is why they no longer travel via `ILogger`) and its nine startup-FAILURE lines, `HttpTransportHost`'s two HTTP startup failures, and `RunSuiteOrchestrator`'s four run-lifecycle records (started / completed / threw / completion-not-recorded — every start pairs with exactly one of the other three, so an unpaired start means "still running or the server died"). **The one-object-per-line claim is scoped to this process's SERVER path** and deliberately excludes the `--validate-worker` / `--spec-index-worker` branches, which are a different process's stderr that the parent captures as data. `runId` is the SERVER-minted id `get_run_status` reports — not the engine's own per-event runId, a disjoint namespace `SuiteEventParser` has never parsed — and `seq` is this server's per-run record ordinal, NOT an engine event ordinal (the engine's events carry no sequence field; the field was renamed from `eventSeq` at the premise check for exactly that reason). The join to the engine's stream stays the registry's `eventsFilePath`. `StructuredLogHygieneSourceGuardTests` pins which files may emit a record and scans them with string literals INTACT (`SourceGuardScan.SourceWithCommentsStrippedOnly`) — the ordinary comment-and-literal-stripping scan blanks `$"…{ex.Message}"` holes and so was blind to the exact shape the guard exists to forbid — with a fail-closed exact-equality allowlist of reviewed-benign matches rather than a narrowed pattern.

**`Transport/`** (Sprint 6, US-S6-06) holds the optional HTTP transport and is built around one rule: **stdio is the default and is untouched by the flag's existence**. `ServerTransportSelection` parses `--transport stdio|http` (absent ⇒ stdio ⇒ **behaviour**-identical to before the story, no configuration — not byte-identical: the flag parse runs and a `--bearer-token` argument is now refused rather than ignored, neither observable on the wire); `http` reads its bearer token ONLY from `VOUCHFX_MCP_HTTP_TOKEN` and **refuses a token passed on the command line** rather than honouring it (argv is world-readable via `/proc/<pid>/cmdline` and `ps`). The token is hashed at parse and the plaintext discarded — the selection carries only a SHA-256 digest, and `PrintMembers` is suppressed so no member can ever reach the record's generated `ToString`. A repeated flag, a token under 16 chars, one with padding, or one carrying non-ASCII is refused. The bind endpoint is parsed here too (default `http://127.0.0.1:5090`, loopback) and configured EXPLICITLY on Kestrel, with the content root pinned to `AppContext.BaseDirectory` and the environment to Production — so a hostile `appsettings.json` in the untrusted CWD cannot rebind the listener or flip the middleware posture. A missing token is a fail-closed startup refusal — catalogued `VFX-E-1007`, non-zero exit, **no listener opened** — which holds because the parse happens at the top of `Program.cs`, before any host is built. `HttpTransportHost` calls the SAME `AddVouchfxMcpServer` the stdio path does (adding `WithHttpTransport()` + `MapMcp("/mcp")` from the exact-pinned `ModelContextProtocol.AspNetCore` 2.2.0), so the two transports cannot drift in the PRIMITIVES they serve — scoped deliberately to that, since the transports are not identical in every respect (stateless mode, and progress-over-HTTP is inferred rather than measured; both recorded in that type's remarks). It has the same fail-closed startup boundary the stdio path does — `RunArtefactStorageException` around registration, and the bind-failure family out of `RunAsync` — each one sanitised JSON line and exit 1, never a stack trace. Both startup banners (pin, containment policy) are emitted ABOVE the transport branch so an HTTP operator gets them too; the bearer gate is registered BEFORE `MapMcp`, which is what makes "rejected before the tool handler runs" structural rather than per-tool. `HttpBearerTokenAuthenticator` compares via `FixedTimeEquals` over SHA-256 digests so the comparison is length-independent (`FixedTimeEquals` short-circuits on unequal lengths and would otherwise leak the token's length); an unauthenticated request gets a bare 401 + `WWW-Authenticate: Bearer` with **no body**, so nothing reveals whether or how a token is configured. `ChildProcessEnvironment` strips the token from every spawned child's environment — the ONE sanctioned exception to the never-touch-a-child's-environment rule, because it REMOVES a secret this server owns rather than injecting into or reading the environment the engine resolves `${secret:env/…}` from. **The MCP Tasks extension is not implemented and cannot be**: measured 2026-09-12 by reflecting the pinned SDK, `ServerCapabilities` exposes exactly `Completions`/`Experimental`/`Extensions`/`Logging`/`Prompts`/`Resources`/`Tools` and there are no Tasks types at all, so that sub-scope is closed **blocked-on-SDK** and polling (`get_run_status`/`cancel_run`) remains the only long-running mechanism; the tripwire is a `TasksCapability` type appearing in a future release. Note the ASP.NET Core package adds a `Microsoft.AspNetCore.App` FrameworkReference to the built app (measured in `runtimeconfig.json`) — satisfied by any machine with the .NET SDK, which is how this tool is installed, and documented in `docs/install.md`.

Hard invariants (all have guard tests):

- **Verdict taxonomy is preserved faithfully**: pass / fail / environment error / inconclusive. Docker-unavailable, timeout, or cancellation is an environment error or inconclusive — never reported as a test failure.
- **Read-only**: the server never writes, modifies, or deletes a suite file — `ReadOnlySourceGuardTests` holds this structurally, scanning `src/` for filesystem-mutation APIs with a fail-closed exact-equality list (only `RunSuiteOrchestrator` and `ScaffoldSuiteOrchestrator` may touch temp artefacts they created themselves; `normalize_suite`'s whole pipeline may not write at all). It never hosts a model — free-text intent is host-LLM territory; `scaffold_suite` takes structured input only.
- **Secret hygiene**: never resolve `${secret:...}`, never read or echo this process's environment into any tool result/progress/resource. The engine is the sole redaction authority; already-redacted event fields are relayed bounded and control-character-sanitised (`TextSanitiser`, `BoundedStreamReader`), never re-redacted or re-resolved. Enforced by `SecretHygieneSourceGuardTests` and `RealSecretHygieneMcpTests`. ONE sanctioned exception, and only in the removal direction: `Transport/ChildProcessEnvironment` strips this server's own `VOUCHFX_MCP_HTTP_TOKEN` from every spawned child's environment — a narrowing of a secret this server owns, never an injection into or a read of the environment the engine resolves `` from, and pinned as the single permitted mutation site across all of `src/`. One measured forward constraint: the engine's `reproducibility-envelope` event carries a `secretReferences` array (the suite's secret-NAME surface — see `RealStepAttemptEnvelopeAgainstPinnedCliTests`); `SuiteEventParser` deliberately does not parse that event type, and any future story that widens the parser or sources `environment` data from it must not relay `secretReferences` into a tool result without a hygiene review.

## Testing conventions

- **No test depends on the real `vouchfx` CLI or Docker.** `McpTestHarness` hosts the real server over in-memory paired streams with a `FakeVouchfxCli` and `FakeSuiteRunner` by default. The `Real*` test-name prefix means "real MCP wire protocol" or "real spawned *vouchfx-mcp* process" (`RepoLayout` derives the built DLL paths — hence build-before-test at the same configuration), **not** the real engine CLI.
- The `*AgainstPinnedCliTests` exceptions — `RealPlanCoverageAgainstPinnedCliTests`, `RealValidateAgainstPinnedCliTests`, `RealGetSchemaAgainstPinnedCliTests`, `RealListStepTypesAgainstPinnedCliTests`, and `RealStepAttemptEnvelopeAgainstPinnedCliTests` (which additionally needs Docker) — self-gate by running the production `CliPinVerifier` against the real PATH and silently pass when the pinned CLI is not installed; do not invent a new skip mechanism for CLI-dependent tests, reuse that pattern. **The guarantees those tests carry are host-conditional**: on a machine without the pinned CLI (and, for the envelope probe, without a container runtime) they are green NO-OPS rather than evidence, which is exactly the CI runners' situation — so a green CI run proves nothing about engine-facing behaviour, and the measured claims they defend (the `step-attempt` envelope's `ts`, the absent `error`, `step-started`'s `timeoutMs`) hold only as of the last time someone ran them on a machine that had both. Issue #40 is the scheduling gap.
- `tests/StdinEofChildFixture/` is a tiny child-process fixture for exercising `VouchfxCliSuiteRunner`'s graceful-stop-then-force-kill against a real OS process.
- `McpServerSkeletonTests` deliberately hardcodes `"0.1.0"` to catch edits to `<Version>`.
- **Run the full suite ONE AT A TIME — never two `dotnet test Vouchfx.Mcp.sln` invocations concurrently.** Measured, twice, during Sprint 5: a second run rebuilds/relinks `bin/Release` under the first, and every class that SPAWNS the built artefact (`Real*` process tests, the validate and spec-index workers) fails against a file being rewritten — roughly 80 bogus failures, plus occasional test-host crashes. Both were investigated as product bugs before the cause was found, which is the expensive part: the failures look exactly like real process-boundary defects and are perfectly reproducible while the collision lasts. If a run must be repeated to check flakiness, repeat it SEQUENTIALLY.

## Versioning and dependency discipline

- `<Version>` (0.1.0) in `Vouchfx.Mcp.csproj` is the single source of truth for `serverInfo.version` in the MCP handshake and is **deliberately decoupled** from `<PackageVersion>` (0.1.0-alpha.1 default, overridden per tag by release.yml). Never let one change as a side effect of the other.
- Package versions are exact-pinned, no wildcards. YamlDotNet is pinned to the same version the engine repo pins (fleet consistency — validation verdicts must not diverge on YAML scalar resolution), and since Sprint 6 that rule is enforced MECHANICALLY by `EngineYamlDotNetPinParityTests` rather than by this sentence: it reads the version out of the vendored schema's own prose at run time and fails if the loaded library is not among the versions the engine names (the policy had silently broken for 46 days before that gate existed); JsonSchema.Net is currently deliberately ahead of the engine's pin (see the csproj comment before touching either).

## Working style in this codebase

- The codebase carries unusually dense rationale comments — files, csproj items, and workflows explain *why* each decision was made and what breaks otherwise. When editing, read the surrounding comment block first (it usually names the constraint you are about to violate) and keep it truthful; several comments encode measured facts ("Verified by re-packing…", dated gotchas).
- Development is spec-first: features land against approved specs in a spec → build → review loop. `specs/` is gitignored (maintainer-local, mirrors the engine repo's convention) and holds the working spec material — currently including the fleet-level vouchfx.ai spec/plan proposals (`specs/vouchfx-ai-mcp-spec.md`, `specs/vouchfx-ai-mcp-plan.md`). Requirement IDs (REQ-NNN/EDGE-NNN) appear throughout code comments and test names. Never move internal material under `docs/` — everything tracked there is auto-published to the public site (see `scripts/build_site.py`).
- `docs/*.md` (overview, install, tools-and-resources, troubleshooting, implementation-map, dsl-guide-for-agents), `docs/validation/*.md` (the graceful-teardown and M4 acceptance drill procedures) and `docs/errors/*.md` (the diagnostic catalogue pages) are the source for the published site at vouchfx-mcp.vouchfx.io; the README's "Status" block is kept current with tool-level detail.
